# TASK-020 — Mid-year school onboarding and opening balances

**Engineering owner:** Fees / Onboarding. **Only technical predecessors:** TASK-013, TASK-019 (all lower numbers). **One execution status tracker:** [TASK-TRACKER.md](../TASK-TRACKER.md). **DLD:** Proposed for official Harness approval.

## 1. Business outcome and use cases

**Deliver this complete, compatible capability now:** Import accurate original-system opening outstanding and optional historical paid references for a school starting ERP mid-year, with preview, reconciliation, provenance and idempotent commit.

**Explicitly out of this task:** No bulk fake SaaS receipts or silent generation of prior months based on guessed amounts. No new student identities when matching imported rows.

**Operator/user story:** As an onboarding administrator, I can import an operating school in August with opening arrears and optionally historical collections so that the ERP starts with accurate balances rather than a blank ledger.

**Use cases with success/error expectations:** UC1: 300 students imported on 2026-08-01; their June–July dues are optionally imported as opening debt, not generated by current tuition rule. UC2: previously paid June receipt exists externally; import as provenance only, no fresh system receipt falsely attributed. UC3: multiple same ledger rows in workbook rejected with line-level errors. UC4: preview totals match source and import commits once. UC5: rollback corrects batch with auditable adjustment, no hard delete.

**Domain rules and acceptance:** Opening balances must not be generated automatically from guessed school fees. Client chooses whether migration contains outstanding balance only or full receipt history, whether previous period paid amounts are trusted, reconciliation signoff and adjustment permissions. Every entry carries source metadata, as-of date, importedBy and original reference. If scope not approved, task BLOCKED.

## 2. Implementation-ready DLD proposal

**Persistence objects, migrations, indexes and invariants:** MigrationBatch(id,schoolId,academicSessionId,asOfDate,sourceSystem,sourceFileId,checksum,status,previewTotals,importedBy,reviewedBy,createdAt,committedAt) and MigrationRow(batchId,rowIndex,studentId,category,period,openingOutstanding,externallyPaid?,reference,rowHash,status,error). FeeCharge.source=OPENING_BALANCE with unique schoolId+batchId+rowHash, and optional HistoricalExternalPayment reference that is excluded from SaaS collection charts unless client approves reporting semantics.

**Typed endpoints and cross-domain facade contracts:** POST /operator/onboarding/opening-balances/upload XLSX private; GET /operator/onboarding/opening-balances/:id/validation; POST /operator/onboarding/opening-balances/:id/preview; POST /operator/onboarding/opening-balances/:id/commit {checksum,expectedTotals,idempotencyKey}; GET /operator/onboarding/opening-balances/:id/results. Do not let imported sheet supply arbitrary schoolId or force a SaaS receiptNumber.

**Detailed service orchestration, server algorithm and frontend states:** Use existing private file store and versioned XLSX parser; normalize student via matched ID/SR + full-name warnings (do not auto-merge uncertain matches); validate decimals/date/categories and duplicate source references; compute before/after ledger diff and require second confirmation; commit in bounded chunks via job/outbox, preserve error rows; only Fees owner posts balances. UI wizard Upload → Validate → Match → Preview → Confirm → Results with clear school-wise reconcile totals.

**Recovery, idempotency, edge/race cases:** Potential legacy student-code collision needs operator review, not merge; imported cash already received must not be counted again as a payment; adding existing debts and back-billing rule simultaneously must not double charge. Allow migrating without Aadhaar.
