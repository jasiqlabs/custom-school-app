## How an intern applies this matrix

1. Find the assigned task row, open the current source files and at least one current `*.spec.ts` in the same domain.
2. Capture behavior of **all listed BASE journeys** BEFORE writing code; create/extend a focused failing regression test and then a new acceptance test.
3. Implement the task's new design in owned modules only, keeping adapter compatibility for legacy endpoints; redesign is allowed if user workflows still work and security/finance history remains intact.
4. Execute focused unit tests, **real Postgres-backed API checks**, actual browser UI journeys, full workspace static/type/build and measured NFR. Run the listed BASE journeys again AFTER.
5. The reviewing engineer must verify before/after evidence and missing cases; if any existing behavior breaks, task remains `QA_FAILED` or `BLOCKED`, not `DONE`.

**Important:** Old code's GET Student Fee Summary may create missing fee dues as a side effect. This is not safe for a report-only role. TASK-001/002/013/019 must prove read-only routes and exports cannot create charges or mutate student/payment records. Typed authorization and school scoping are necessary, not just hidden UI controls.

**Documentation QA note:** A static path match does not prove code compiles, legacy flows actually work or current integration tests cover them. All runtime evidence remains pending until performed by the implementation team.
