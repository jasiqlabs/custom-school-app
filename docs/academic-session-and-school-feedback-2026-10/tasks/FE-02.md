# FE-02 — One-time admission and registration charges

**Evidence:** Chat item 4, registration/admission one-time fees. **Execution:** [TASK-TRACKER](../TASK-TRACKER.md). **Authority:** Proposed only until PRD/HLD/story/UIUX/DLD gates approved. **Current touch points:** admit-student.service.ts, fee category and FE-07 ledger, student profile fee summary.

## Requirement, actors, real-world use cases
**Business story:** When school registers a pupil, it records configured one-time registration/admission charges exactly once for the approved policy scope.

**Use cases and acceptance examples:** UC1: new admission includes registration ₹400 and admission ₹500 on student's statement. UC2: incomplete admission transaction retries, no duplicated ₹900. UC3: repeat/re-admission in next year does not reapply lifetime one-time fees unless client decides otherwise. UC4: school has no admission fee rule, no phantom zero due.

**Business invariants, eligibility, scope and denial conditions:** Client must confirm one-time scope: lifetime in school vs each re-entry or session. Idempotent posting based on immutable business key; paid amounts never regenerated. Student admission success cannot silently leave half-created one-time obligations.

## Detailed design: domain, schema, interfaces and UI
**Database schema / constraints / existing-data migration:** FeeCharge sourceKey composed (schoolId,studentId,category,oneTimePolicyScope) UNIQUE, plus originAdmissionEventId/ref, rules/snapshot; prevent two identical charge keys even across race; fee receipts link through FE-07 allocations.

**Exact proposed endpoint contract, input/output, role/tenant validation:** Admission response includes `chargesPreview` and `chargesCreated` from fee facade; GET /operator/students/:id/fees/statement. Fee rule setup already supplies school-approved amount; do not trust UI-supplied total. Reject cross-tenant charge ID.

**Service algorithm, module ownership and external integration / UI flow:** Students admission service calls FeesPublicFacade.postInitialCharges via transaction coordinator or post-commit transactional outbox; choose architecture ensuring eventual consistency with explicit PendingFinancialSetup status and safe retries; not direct fees repository write. Web admission confirmation shows one-time charges & next steps. Retry returns identical source IDs.

**Concurrency, edge cases, failure handling and idempotency:** Student reactivation via CL-04, unique Student Code changes, and bulk import call same billing code path. Failure halfway in fee posting must be observable/replayed without duplicate student/admission fee.
