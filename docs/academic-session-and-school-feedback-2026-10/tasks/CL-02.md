# CL-02 — Fee start/stop and class changes within the academic year

**Authority:** PDF clarification 5 (page 3) — NEW gap; AS-05 only handled year-to-year continuity. **Status:** see [single task tracker](../TASK-TRACKER.md). **Required approval:** client scope + Harness PRD/HLD/story/UIUX/DLD revision. **Relevant current code:** StudentsPublicFacade enrollment effective dates; FeesPublicFacade charge engine; TransportPublicFacade.

## 1. Requirement and operator story
As a school manager, I charge a child only for school attendance/service-eligible months, including mid-year admission, intra-year class change and leaving.

**Use cases with expected outcomes:** UC1: admitted August: fees for August onward under confirmed charging convention, not April–July. UC2: leaves in November: December tuition/transport not generated, but October unpaid remains. UC3: changes Class 2 to Class 3 mid-October: October charged according to approved boundary rule, November at new class rate. UC4: late backdated changes require preview adjustments, not silently recalculating receipts.

## 2. Exact functional acceptance boundaries
**Client must specify** first billable month, final month, partial-month prorating (if any), backdating, charge class-selection effective date. Policy is school-scoped/versioned, never hard-coded and never retroactively changes paid lines without approved adjustment. No automatic fee charge outside active enrollment and enabled fee rule applicability.

## 3. Detailed technical design — data, contracts, algorithm and UI

**Ownership and persistence / migrations:** Enrollment with validFrom/validTo DATE and reason. FeeEligibilityPolicy(schoolId,policyVersion,startConvention,endConvention,changeConvention,prorationRule?) with approved enum values; FeeCharge records ruleVersion, classSnapshot, enrolledPeriod, category, originSession and dueDate. For mid-year class change use an enrollment segment per effective change.

**API and typed validation:** GET /operator/students/:id/fees/eligibility-preview?from&to; manager POST /operator/students/:id/enrollments/change-class {effectiveDate,newClassId,newSectionId,expectedVersion}; charge generator consumes StudentEnrollmentEligibilityPort by bounded period batches; updates display estimated old/new month impact.

**Service algorithm, cross-module integrations, frontend screen state:** Admission writes start eligibility; class-change workflow validates effective date against session and prevents overlapping enrollment segments; fee generator requests eligible class-at-period from Students public port, selects corresponding FeeRule, charges idempotent sourceKey. Exit workflow publishes stop-effective event. Backdated corrections use diff preview and FeeAdjustment, not delete.

**Edge cases, consistency and recovery:** Transport fee may need different start/stop policy than tuition; one-time admission and registration do not repeat monthly; opening-balance items are pre-existing obligations. No assumption that August admission owes earlier months even when fee config effective April.

## 4. Verification matrix (named tests)

**Frontend (FE) test plan:** TC-CL02-FE01 admit Aug shows months Aug+ only; FE02 exit Nov preview tells future fee stop; FE03 class change Oct shows policy; FE04 date validation and double submit; FE05 wrong session/closed-year warning.

**Backend (BE, DB, integration, API, security) test plan:** TC-CL02-BE01 all 12 calendar boundaries, leap February, March-April session boundaries; BE02 class effective segment join; BE03 no charges pre-admission/post-exit; BE04 retries no duplicates; BE05 changing already paid month creates adjustment only.
