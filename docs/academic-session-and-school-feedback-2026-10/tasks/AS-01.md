# AS-01 — Define school-owned academic sessions and calendar

**Authority:** PDF clarification 1 (page 2); existing AS-01. **Status:** see [single task tracker](../TASK-TRACKER.md). **Required approval:** client scope + Harness PRD/HLD/story/UIUX/DLD revision. **Relevant current code:** prisma/schema.prisma; apps/api/src/modules/platform-admin/academics/academics.service.ts; school web academic screens.

## 1. Requirement and operator story
As a school manager, I configure 2026–27 and 2027–28 separately for my school, without changing another school's dates.

**Use cases with expected outcomes:** UC1: newly onboarded school creates 2026–27 with 2026-04-01..2027-03-31 and verifies state DRAFT. UC2: a second school chooses June-May dates. UC3: duplicate code, reversed date and overlapping ACTIVE periods are rejected. UC4: migrated tenant has older enrollment but no known historic dates; operator sees review-required mapping rather than fabricated history.

## 2. Exact functional acceptance boundaries
Sessions belong to precisely one School; code is a string, label editable, fixed start/end once ACTIVE unless exceptional governed correction. School clock uses Asia/Kolkata calendar DATE. Only one ACTIVE school session; school may hold future DRAFT sessions. Scope awaits client current/next-phase decision.

## 3. Detailed technical design — data, contracts, algorithm and UI

**Ownership and persistence / migrations:** AcademicSession {id UUID PK,schoolId UUID composite school FK,code varchar(32),label varchar(100),startDate DATE,endDate DATE,status DRAFT|ACTIVE|CLOSING|CLOSED,version int,createdBy UUID,activatedAt timestamptz?,closedAt?,createdAt,updatedAt}; UNIQUE(schoolId,code); CHECK(startDate<=endDate); partial unique index for ACTIVE status (coordination AS-02). Legacy enrolments receive nullable session FK in AS-03, NOT a guessed current session.

**API and typed validation:** GET /operator/academic-sessions (read/list, pagination); POST /operator/academic-sessions {code,label,startDate,endDate}; PATCH /operator/academic-sessions/:id {version,label?,startDate?,endDate?}; GET /operator/academic-sessions/:id. Schema returns schoolId/id/status/version/date as YYYY-MM-DD; 422 invalid date, 409 duplicate/version, 404 cross school.

**Service algorithm, cross-module integrations, frontend screen state:** Controller reads actor.schoolId, role=MANAGER. Zod parse and calendar validation -> AcademicsSessionService -> Prisma transaction with audit outbox. No sibling module direct persistence. UI Academic Sessions screen: list, new session form, labelled dates, drafts/active/closed badges, explanatory empty state, confirmation before submit; use shared routing header.

**Edge cases, consistency and recovery:** Do not conflate UserSession login expiration with school year; never infer session from server clock; all legacy schools need compatibility/transition plan. Draft editing must not change a year already issued on frozen documents.

## 4. Verification matrix (named tests)

**Frontend (FE) test plan:** TC-AS01-FE01 create and read back dates; FE02 invalid reversed dates reveals actionable inline error; FE03 two schools have distinct calendars; FE04 responsive 360/768/1366, tab & screenreader; FE05 default empty state indicates setup rather than missing student data.

**Backend (BE, DB, integration, API, security) test plan:** TC-AS01-BE01 2 tenants cannot read/write each other's year UUID; BE02 duplicate code concurrent insert loses with 409; BE03 DATE boundaries March-April; BE04 version stale update 409; BE05 audit and rollback on failed insert.

**Nonfunctional (NFR, load, reliability, privacy, accessibility) test plan:** TC-AS01-NFR01 indexed list as 10k-school synthetic multi-tenant set; NFR02 preserve 99.5% availability deployment target; NFR03 no destructive schema/data migration; NFR04 private no-store, CSRF and role checks; compare p95 with baseline and document actual.
