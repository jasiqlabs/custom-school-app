# FB-06 — Download PDF receipt from payment history

**Evidence:** DOCX page 4. **Execution:** [TASK-TRACKER](../TASK-TRACKER.md). **Authority:** Proposed only until PRD/HLD/story/UIUX/DLD gates approved. **Current touch points:** apps/web/src/app/operator/fees/history/ui.tsx, FeesController receipt getter, private file storage.

## Requirement, actors, real-world use cases
**Business story:** An authorized operator opens payment history and downloads a verifiable receipt as a PDF instead of relying only on print dialog.

**Use cases and acceptance examples:** UC1: click Download next to one payment, browser saves e.g. fee-receipt-000123.pdf. UC2: download a VOIDED receipt, clearly marked. UC3: report-viewer can only download if receipts explicitly included in approved reports. UC4: signed URL expires and retry renews after auth. UC5: foreign school payment denied.

**Business invariants, eligibility, scope and denial conditions:** New per-payment download is in scope; not necessarily bulk ZIP/PDF or CSV export. Format must be same receipt view as FB-05. No public URL exposing student name/ID; output filename sanitized. Preserve current View/Print action.

## Detailed design: domain, schema, interfaces and UI
**Database schema / constraints / existing-data migration:** Reuse private SchoolFile of type RECEIPT and optionally ReceiptRender(jobId, paymentId, templateVersion, fileId, checksum,status) unique per frozen receipt version; if generated synchronously, no persisted file required but content must still be immutable. No new mutable money fields.

**Exact proposed endpoint contract, input/output, role/tenant validation:** GET /operator/fees/payments/:id/receipt.pdf with response application/pdf, Cache-Control private,no-store and Content-Disposition attachment; if async render use POST /operator/fees/payments/:id/receipt-render and authorized short-lived GET download/status; no anonymous file serving.

**Service algorithm, module ownership and external integration / UI flow:** History action cell adds Download button with loading/error and fetch as Blob/stream; server calls Fees ReceiptAssembler then versioned PDF renderer/worker. Store/retrieve via PrivateFileService after tenant and role check; generate URL with short TTL. One shared rendered data contract with FB-05 ensures print/download match.

**Concurrency, edge cases, failure handling and idempotency:** If rendering pending show deterministic queue state; repeated download uses same snapshot and does not create duplicate receipt/payment; safari/mobile file behavior needs manual test; old payment may require legacy fallback data.
