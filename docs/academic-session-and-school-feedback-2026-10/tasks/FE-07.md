# FE-07 — Multi-line charge ledger, allocations and financial reconciliation

**Trace to source:** Technical foundation necessary for Chat items 4–6, receipt redesign, TC/admit clearance and academic continuity.. **State and owner:** [TASK-TRACKER](../TASK-TRACKER.md) is authoritative. **Baseline files:** prisma ClassFeeConfig/FeeDue/FeePayment, collect-payment.service.ts, void-payment.service.ts, FeeRepository, contracts fee.types.ts. **No feature implementation implied by planning completion.**

## 1. Detailed requirement and use-case definition
**User story:** School can owe multiple independent amounts in same month, pay several line items under one receipt, void safely, and retain a verifiable history despite billing rule changes.

**Real school scenarios:** UC1: student owes tuition ₹700, transport ₹150 and exam ₹100 in same month (all distinct charges). UC2: one ₹500 payment applied ₹350 tuition + ₹150 transport; receipt total ₹500 and outstanding ₹450. UC3: replay with same idempotency key yields existing receipt; not a second payment. UC4: void restores each original charge amount and preserves receipt number. UC5: migrate 20 old monthly fees without changing customer balance/receipt IDs.

**Rules/eligibility/out-of-scope decisions:** Financial authority is FeeCharge+active payment allocations+explicit adjustments. No JS floating-point calculations for posting; Decimal(12,2)/minor units with exact rounding. Every POST school-scoped and atomic with row locks; no arbitrary overpayment or negative charge. Migration dual-reading must never double count old FeeDue and migrated new FeeCharge. Approved old same-day void policy retained.

## 2. Detailed Level Design (proposed until approved by Harness)
**Persistent data model, uniqueness, indexing, migration:** FeeCharge(id,schoolId,studentId,academicSessionId?,classId?,categoryId,ruleId?,sourceKey,originRef,periodStart DATE?,periodEnd?,dueDate DATE,baseAmount NUMERIC12,2,concessionAmount,fineAmount,netAmount,paidAmount,balance,status,version,createdAt) UNIQUE(schoolId,sourceKey); CHECK(net>=0,paid>=0,balance>=0,paid+balance=net) validated database/service. FeePaymentAllocation(id,paymentId,chargeId,amount NUMERIC12,2,voidReversedAt?,schoolId) UNIQUE(paymentId,chargeId), nonzero amount. FeePayment current rows retained with legacy dueId during expand; add optional payment-snapshot/collector and mapping table LegacyDueChargeMap(legacyDueId,chargeId) to reconcile; ensure composite same-school relations. ReceiptNumber allocator retained then versioned under CL-06.

**REST/port contract, actor authorization, DTOs and error semantics:** GET /operator/fees/students/:studentId/statement {charges,balances,period,originSession}; POST /operator/fees/payments {studentId,idempotencyKey,paymentDate,mode,allocations:[{chargeId,amount}],reference?}, response PaymentReceiptDto with immutable allocated line snapshots. POST /operator/fees/payments/:id/void replays original allocations atomically. Keep old {dueId,amount} API path behind compatibility adapter during cutover; typed 409 overpay/replay hash mismatch, 422 invalid allocation.

**Backend workflow, module responsibilities, frontend states and integration strategy:** Fees service selects target FeeCharge rows by school+student+IDs, sorts IDs and SELECT FOR UPDATE, validates remaining balances and same actor/tenant, locks receipt sequence, writes FeePayment, FeePaymentAllocation, charge balances and audit outbox in ONE SQL transaction. Backfill shadow FeeCharge/allocations from original FeeDue/Payment with original amounts and dates, compare counts/totals/void states per school, cutover with feature flag only when exact reconciled. Read old and new via one unified facade; UI multi-selection summary, payment allocation preview, receipt view composer, refresh statement after post/void. Students/TC only consume FeesPublicFacade, never direct fees persistence.

**Race conditions, failure cases, transaction/retry/rollback semantics:** Two simultaneous payment requests for same charge cannot overpay; same key different request hash 409, exact same key returns original receipt. Void once under Asia/Kolkata same-day policy, preserve historic number and line item data. Paid source charge must not be modified in place on concession/rule edit; use adjustment or forward billing. Migrated old receipt initially lacks allocation array; projection builds equivalent single line.
