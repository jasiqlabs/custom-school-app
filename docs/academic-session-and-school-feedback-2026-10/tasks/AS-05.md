# AS-05 — Financial continuity across closed and new academic sessions

**Authority:** PDF clarifications 1,3,5 and previous project discussion. **Status:** see [single task tracker](../TASK-TRACKER.md). **Required approval:** client scope + Harness PRD/HLD/story/UIUX/DLD revision. **Relevant current code:** FeesPublicFacade, FeeCharge/allocations FE-07, FeeStatement, AcademicSession lifecycle.

## 1. Requirement and operator story
As a manager, I start a new academic year without losing previous fee balances or double-charging a student.

**Use cases with expected outcomes:** UC1: 2026–27 old ₹400 unpaid and 2027–28 ₹900 tuition -> statement ₹1300 with original origin sessions. UC2: pay ₹400 in 2027–28, old charge closes, new remains. UC3: closed year report still shows as-of-close outstanding vs today's remaining, clearly labelled. UC4: previous paid receipts remain immutable.

## 2. Exact functional acceptance boundaries
No copying arrears to next-year charge records; new charges reference origin session; payment can allocate to old charges when school policy permits; accounting date and origin fee session are different. Annual closure must never write off charges.

## 3. Detailed technical design — data, contracts, algorithm and UI

**Ownership and persistence / migrations:** FeeCharge.originSessionId UUID FK, servicePeriod start/end/date and immutable billed amount. FeePaymentAllocation appliedOn timestamp and optional collectionSessionId as contextual metadata. SessionCloseSnapshot aggregate counts/hash generated from fee facade for frozen as-of reporting, not source of truth for live balances.

**API and typed validation:** FeesPublicFacade.getStatement({schoolId,studentId,asOfDate,includeClosedSessions:true}); GET /operator/fees/statements/:studentId?academicSessionId; GET /operator/academic-sessions/:id/closing-financial-summary. Response splits originSession, chargePeriod, paid/outstanding.

**Service algorithm, cross-module integrations, frontend screen state:** Fees owner builds SQL over ledger with session filter, allocations, and cutoffs. Academics close-preview calls fees facade only, never fee tables. Web statement groups older-session arrears separately, total remains sum of source charge balances. Receipts always use payment-time source allocation snapshots.

**Edge cases, consistency and recovery:** What happens when prior balances legally written off or conceded requires explicit adjustment with actor/reason, not direct status PAID. Financial-year numbering is a separate CL-06 policy.

## 4. Verification matrix (named tests)

**Frontend (FE) test plan:** TC-AS05-FE01 older/newer session statement correct; FE02 receipt after old-fee payment identifies year; FE03 close preview shows arrears vs locked snapshots; FE04 no double charge in category cards.

**Backend (BE, DB, integration, API, security) test plan:** TC-AS05-BE01 strict arithmetic invariant; BE02 no duplicate charge after close/create; BE03 partial + void on historic charge; BE04 cross-year assignment joins school safe; BE05 no direct student table access in fees.

**Nonfunctional (NFR, load, reliability, privacy, accessibility) test plan:** TC-AS05-NFR01 24–60 months ledger query plan; NFR02 stress 10 parallel mixed-year payments; NFR03 daily reconcile alerts; NFR04 restore test with old charge snapshots.

## 5. Migration, release and regression requirements
Run additive migration and seed two isolated schools, previously active student & fee histories. Demonstrate existing platform-admin, school-operator login, legacy student search/import, monthly fee collection, transport assignment, existing TC download, receipt numbering and dashboard remain functional, as applicable. Cross-school object IDs must always be rejected (generic 404), mutation endpoints must require capabilities and CSRF, and audit/payment integrity remains intact. Record reproducible commands, expected/actual outputs and adverse test results in the sole TASK-TRACKER; no code is claimed implemented by this document.
