# FB-05 — Office/Student copy printable receipt with ₹ and operator name

**Evidence:** DOCX page 3 sample; chat fee category feedback. **Execution:** [TASK-TRACKER](../TASK-TRACKER.md). **Authority:** Proposed only until PRD/HLD/story/UIUX/DLD gates approved. **Current touch points:** collect-payment.service.ts buildReceiptDto; apps/web/operator/fees/collect/ui.tsx and history/ui.tsx; FeePayment.createdBy.

## Requirement, actors, real-world use cases
**Business story:** A fee collector must print a professional two-copy receipt showing school header, fee components, paid/due summary, who collected payment and correct currency.

**Use cases and acceptance examples:** UC1: new fee payment spanning registration and monthly tuition prints Office Copy and Student Copy with identical receipt number and total. UC2: exact operator full name appears on both copies, not email or stale name. UC3: voided receipt is clearly marked VOIDED. UC4: legacy single-month receipt still prints. UC5: 20 fee lines wrap without clipping, amount in words matches paise.

**Business invariants, eligibility, scope and denial conditions:** One immutable payment receipt, two named copies in one PDF/print view; currency glyph presumed ₹ but PDF source text extracted '?' — confirm before template approval. Never fabricate principal signature. Historical receipts remain meaningful even if collecting operator changes name/deletes account. Separate issued receipt vs outstanding at time of print to avoid today's balance distorting old receipt.

## Detailed design: domain, schema, interfaces and UI
**Database schema / constraints / existing-data migration:** Add FeePayment.collectorNameSnapshot varchar(255) optional, receiptTemplateVersion, schoolBrandSnapshot? as versioned encrypted/JSON metadata where appropriate; allocation snapshot includes category/charge period, gross, concession, fine and allocated paid; aggregate amounts derive immutable receipt snapshot. Existing FeePayment.createdBy UUID resolves legacy operator name if still present, with historical fallback.

**Exact proposed endpoint contract, input/output, role/tenant validation:** Extend GET /operator/fees/payments/:id/receipt with versioned ReceiptViewDto {school,receiptNumber,issuedAt,studentSnapshot,collectedBySnapshot,rows:[{category,period,assigned,concession,fine,received}],totals:{assigned,discount,net,paidThisReceipt,paidToDate,balanceAsOfReceipt},status}. Auth manager or explicitly approved report access, no-store, school scope.

**Service algorithm, module ownership and external integration / UI flow:** BuildReceiptDto moves to one FeesOwned ReceiptAssembler; do not duplicate computation in React. Next.js one shared ReceiptPrint component for collection/history, CSS @media print A4 with explicit page breaks: Office Copy header dark/navy, Student Copy green per sample; operator name and amount in words. Always include print-safe ₹ font/glyph and 'Copy' labels; void state watermark. Use versioned renderer for legacy records.

**Concurrency, edge cases, failure handling and idempotency:** One payment can allocate across many fee charges FE-07; show each row without double counting concessions; void prints original data plus void metadata, not zero paid. Long school address/signature, logo aspect ratio, browser PDF print differences.
