# CL-04 — Reactivation and re-admission to a new school session

**Source:** PDF clarification 7 (page 3); previously omitted.. **Work status:** [single tracker](../TASK-TRACKER.md). **Approval required:** update Harness authority before implementation. **Current code / owner:** change-student-status.service.ts, student enrollment/profile, admission fee and transport port.

## Business goal, concrete use cases and acceptance
**User story:** As school manager, I readmit a student who previously left without losing old student identity, classes, TC, fee or transport history.

**Use cases and expected results:** UC1: child left in 2026-27, returns in 2027-28 to Class 3-B. UC2: return in same session after temporary inactive state, requires explicit effective dates. UC3: old debts remain visible and admission charges behave per one-time policy. UC4: tries to reactivate student currently enrolled in another active class -> conflict. UC5: returning student chooses transport anew, not silently reactivate old route.

**Business policy and acceptance rules:** Status ACTIVE toggle alone is insufficient: must specify target session, class, section, reentry date and reason. Do not generate duplicate Student UUID/code; no default re-use of old class or transport assignment. Enforce new-year closure/eligibility and fees start rule CL-02.

## Detailed Level Design (proposed until approved)
**DB schema, indexes and migration/backfill:** StudentReAdmission(id,schoolId,studentId,targetSessionId,effectiveDate,reason,createdBy,previousExitId?,status,version); new StudentEnrollment with target period and preserved prior rows. If repeated in same target year, enforce no date overlap (SQL unique/constraint or explicit lock + composite business key).

**API/routes/contracts, validation and authorization:** GET /operator/students/:id/reactivation-preview?targetSessionId; POST /operator/students/:id/reactivate {targetSessionId,classId,sectionId,effectiveDate,reason,requestKey,expectedStudentVersion}; GET /operator/students/:id/enrollment-history.

**Frontend screens, backend service orchestration, ports/facades and processing algorithm:** Students service fetches existing identity, validates inactive/left and target session ACTIVE via AcademicsPublicFacade, loads class/section and eligibility, locks existing enrollments, creates new enrollment and records re-admission event; fee start event passed to FeesPublicFacade and optional new transport assignment staged through transport owner. UI 'Reactivate Student' multi-step chooses year/class/section, displays previous status and debts, requires confirmation.

**Errors, edge cases, reconciliation and recovery design:** Prior TC still authentic historic issue; new TC may be issued after return per policy. Paid previous registration/admission fees should not repeat unless client explicitly approves re-enrollment policy. Race of two reactivate clicks must create one result.
