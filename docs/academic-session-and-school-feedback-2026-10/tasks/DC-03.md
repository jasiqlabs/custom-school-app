# DC-03 — Admit Card Generator (separately chargeable CR)

**Source:** Client Chat item 1 and explicit scope/pricing note. **Commercial gate:** BLOCKED pending written approval. **Existing PRD:** exams out of MVP scope. **Status:** [tracker](../TASK-TRACKER.md).

## Requirements and detailed use cases

After commercial approval, a school MANAGER may set a minimal exam context, choose the relevant academic session/classes and students, preview, generate, print and download an official admit card. This is **audio? No** — an exam document only, not a complete examinations, marks, attendance or grading module.

- **UC-01:** Define school exam title, dates, centre/venue, session and class; generate one pupil's branded admit card.
- **UC-02:** Select 20 students in same class, one failed readiness or outstanding fee → return per-student eligible/blocked results when batch explicitly approved.
- **UC-03:** Change school address/student class after issue → previously issued PDF retains issued-at data; reissue requires explicit user action.
- **UC-04:** Blank subject timetable or missing candidate roll number must not be invented; block if approved template requires fields.
- **UC-05:** Report-viewer and another school's manager cannot issue/download other tenants' cards.

## DLD / architecture proposal

**Ownership:** Distinct `AdmitCard` document capability, optionally embedded in Documents owner, exposes a public issue interface. It consumes SchoolInfoPublicFacade, StudentsPublicFacade.getEnrollmentSnapshot, AcademicSessionPublicFacade and FeesPublicFacade.checkDocumentClearance(ADMIT_CARD). No direct private repository access across domains.

**New persistence only after approval:** `ExamCardContext(id,schoolId,academicSessionId,title,examCode,dateStart,dateEnd,venue,instructions,templateVersion,status,version)`, optional `ExamSubjectSlot(contextId,subject,date,startAt,endAt,room)` if client approves timetable. `AdmitCardIssue(id,schoolId,studentId,contextId,issuedAt,issuedBy,issuedByType,immutableEncryptedSnapshot,cryptoKeyVersion,templateVersion,status,jobId,fileId,checksum,requestKey)`; index school/context/student; unique idempotency key while permitting deliberate reissue. Extend private `FileType.ADMIT_CARD`, `JobType.ADMIT_CARD_PDF` only when CR approved. Student Aadhaar is never printed by default.

**API:** GET/POST/PATCH `/operator/admit-cards/exams` (only minimal metadata), GET `/operator/admit-cards/eligible-students?examContextId`, POST `/operator/admit-cards/issue {contextId,studentIds,requestKey}`, GET `/operator/admit-cards/issues/:id` and `.../:id/download`. Strict tenant and session FK validation and capability `admitcard:issue`; GET download private/authorized; 409 on dues, 422 on missing template data.

**Service algorithm:** Validate configured exam/session → validate student enrollment for session+class → DC-04 fee eligibility → freeze school/child/exam/schedule/policy evidence → create issue + outbox job in transaction → trusted worker receives jobId only, loads encrypted snapshot, renders versioned PDF, stores school-private file with checksum → transition COMPLETED/FAILED. Retries use original snapshot; no new issue unless explicitly requested.

**FE flow:** Operator > Admit Cards > Select Exam > Choose Session/Class > Select Student(s) > Preview PDF > Fee-Clearance Review > Confirm > Generation Status / Download. Include progress for approved batch, error descriptions and retry. Mobile/tablet/desktop responsive, print A4 and correct operator language; exact template layout requires client sign-off.

**Unresolved decisions:** Required fields on admit card; subject-wise vs generic exam date; number/roll format; one-by-one vs bulk; template language/brand; whether exam metadata can be edited after issue; approval/price. None of these defaults are client-approved.
