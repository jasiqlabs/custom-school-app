# CL-03 — Mid-year onboarding, historical obligations and opening balances

**Source:** PDF clarification 6 (page 3); previously omitted.. **Work status:** [single tracker](../TASK-TRACKER.md). **Approval required:** update Harness authority before implementation. **Current code / owner:** student-import.service.ts, fee repository, School onboarding, audit/private XLSX infrastructure.

## Business goal, concrete use cases and acceptance
**User story:** As an onboarding administrator, I can import an operating school in August with opening arrears and optionally historical collections so that the ERP starts with accurate balances rather than a blank ledger.

**Use cases and expected results:** UC1: 300 students imported on 2026-08-01; their June–July dues are optionally imported as opening debt, not generated by current tuition rule. UC2: previously paid June receipt exists externally; import as provenance only, no fresh system receipt falsely attributed. UC3: multiple same ledger rows in workbook rejected with line-level errors. UC4: preview totals match source and import commits once. UC5: rollback corrects batch with auditable adjustment, no hard delete.

**Business policy and acceptance rules:** Opening balances must not be generated automatically from guessed school fees. Client chooses whether migration contains outstanding balance only or full receipt history, whether previous period paid amounts are trusted, reconciliation signoff and adjustment permissions. Every entry carries source metadata, as-of date, importedBy and original reference. If scope not approved, task BLOCKED.

## Detailed Level Design (proposed until approved)
**DB schema, indexes and migration/backfill:** MigrationBatch(id,schoolId,academicSessionId,asOfDate,sourceSystem,sourceFileId,checksum,status,previewTotals,importedBy,reviewedBy,createdAt,committedAt) and MigrationRow(batchId,rowIndex,studentId,category,period,openingOutstanding,externallyPaid?,reference,rowHash,status,error). FeeCharge.source=OPENING_BALANCE with unique schoolId+batchId+rowHash, and optional HistoricalExternalPayment reference that is excluded from SaaS collection charts unless client approves reporting semantics.

**API/routes/contracts, validation and authorization:** POST /operator/onboarding/opening-balances/upload XLSX private; GET /operator/onboarding/opening-balances/:id/validation; POST /operator/onboarding/opening-balances/:id/preview; POST /operator/onboarding/opening-balances/:id/commit {checksum,expectedTotals,idempotencyKey}; GET /operator/onboarding/opening-balances/:id/results. Do not let imported sheet supply arbitrary schoolId or force a SaaS receiptNumber.

**Frontend screens, backend service orchestration, ports/facades and processing algorithm:** Use existing private file store and versioned XLSX parser; normalize student via matched ID/SR + full-name warnings (do not auto-merge uncertain matches); validate decimals/date/categories and duplicate source references; compute before/after ledger diff and require second confirmation; commit in bounded chunks via job/outbox, preserve error rows; only Fees owner posts balances. UI wizard Upload → Validate → Match → Preview → Confirm → Results with clear school-wise reconcile totals.

**Errors, edge cases, reconciliation and recovery design:** Potential legacy student-code collision needs operator review, not merge; imported cash already received must not be counted again as a payment; adding existing debts and back-billing rule simultaneously must not double charge. Allow migrating without Aadhaar.
