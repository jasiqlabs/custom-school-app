# CL-05 — School onboarding go-live readiness check

**Source:** PDF clarification 8 (page 3); previously omitted.. **Work status:** [single tracker](../TASK-TRACKER.md). **Approval required:** update Harness authority before implementation. **Current code / owner:** schools.service.ts activate school, class/section, operator provisioning and AS-01.

## Business goal, concrete use cases and acceptance
**User story:** As platform admin, I get a clear checklist before activating a new school so I don't provision a technically active but unusable tenant.

**Use cases and expected results:** UC1: new school has name but no active session/classes; readiness shows deficiencies. UC2: school has no operator yet because existing provisioning requires ACTIVE school — activation must not deadlock. UC3: legacy ACTIVE school missing session remains operational in compatibility mode until migrated. UC4: activation review confirms optional vs mandatory criteria.

**Business policy and acceptance rules:** Client must classify each criterion mandatory/warning. Current code requires school ACTIVE *before* creating operator, so requirement 'operator before activation' contradicts existing order. Design must resolve with safe provisional operator (INACTIVE until school active) or revised activation protocol; never strand first tenant. Existing ACTIVE schools grandfathered with warnings, not suddenly disabled.

## Detailed Level Design (proposed until approved)
**DB schema, indexes and migration/backfill:** SchoolReadinessCheck view/dto, derived from authoritative School, AcademicSession, classes/sections, operators, logo/principal if required. Optional audit row SchoolActivationReview(schoolId,version,criteriaVersion,blockingCodes,warnings,acknowledgedBy,time); no redundant mutable 'readiness' flag in school unless cached revisioned projection.

**API/routes/contracts, validation and authorization:** GET /platform/schools/:id/readiness; POST /platform/schools/:id/activate {expectedVersion,readinessVersion,confirmWarnings}; preserve existing status route with compatible validation. Operator bootstrap via pre-activation provisioned status if approved, activated once school active.

**Frontend screens, backend service orchestration, ports/facades and processing algorithm:** Readiness composer uses school-owned data and AcademicsPublicFacade; returns codes e.g. MISSING_ACTIVE_YEAR / NO_ACTIVE_CLASS / NO_SECTION / NO_OPERATOR (if supported), minRequired true/false per config. Platform admin UI card with checklist, links to fix, warning vs blocker, confirm; atomic activation re-evaluates readiness under school row lock.

**Errors, edge cases, reconciliation and recovery design:** Avoid false-negative when deliberate school without transport/fee configs; readiness should not require features the school won't use. School deactivation/reactivation uses same logic but legacy access policy agreed. Operator-creation deadlock is a P0 architecture decision.
