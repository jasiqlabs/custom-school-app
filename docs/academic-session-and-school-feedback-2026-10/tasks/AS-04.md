# AS-04 — Bulk promotion, repeat, pass-out and year transition

**Authority:** PDF clarification 2 (page 2). **Status:** see [single task tracker](../TASK-TRACKER.md). **Required approval:** client scope + Harness PRD/HLD/story/UIUX/DLD revision. **Relevant current code:** StudentEnrollment service; AcademicSession facade; transport and fee public services; BullMQ job infrastructure.

## 1. Requirement and operator story
As a manager, I review all students at year-end, promote some, repeat some, graduate others, and explicitly handle transfers without creating duplicate students.

**Use cases with expected outcomes:** UC1: 30 Class 1 students move to Class 2, 2 repeat Class 1, 1 passes out. UC2: student moves sections without class promotion. UC3: operator retries failed bulk commit after connection loss. UC4: duplicate same-student selection rejected. UC5: records are audited for individual correction without undoing fee receipts.

## 2. Exact functional acceptance boundaries
Batch transitions require approved source+target sessions, target class+section for PROMOTE/REPEAT, explicit PASS_OUT/LEFT states, exception confirmation and unique request idempotency. No implicit TC issue for passed-out student; no source history deletion. No promotion if target enrollment already exists.

## 3. Detailed technical design — data, contracts, algorithm and UI

**Ownership and persistence / migrations:** SessionTransitionBatch(id,schoolId,sourceSessionId,targetSessionId,operatorId,idempotencyKey,requestHash,state,summary,createdAt,committedAt); SessionTransitionItem(batchId,studentId,decision,targetClassId,targetSectionId,version,status,errorCode). UNIQUE(schoolId,idempotencyKey), UNIQUE(batchId,studentId); bounded processing with replay markers.

**API and typed validation:** GET /operator/academic-sessions/:id/promotion-candidates?targetSessionId, POST .../promotion-preview {items}, POST .../promotion-commit {reviewToken,idempotencyKey}, GET .../promotion-batches/:batchId. Typed 409 stale enrollment, conflict, closed target; 422 invalid destination; 404 cross school.

**Service algorithm, cross-module integrations, frontend screen state:** Preview fetches student snapshots by facade, checks section, school, status, target session. Commit revalidates versions, locks in deterministic order, ends source row and creates target row only if promote/repeat; for pass-out coordinate exit lifecycle CL-01. Batch engine persists per-row result and exposes retry failed rows only. UI editable grid with explicit actions, count summary and 'Review and confirm' flow.

**Edge cases, consistency and recovery:** Fees and transport follow their OWN eligibility rules; promotion never copies debts as new charges. Promote of CLOSED source requires authorized close process sequencing. Handle previous-year student with unpaid balance but still promoting; client decision determines warning vs block.
